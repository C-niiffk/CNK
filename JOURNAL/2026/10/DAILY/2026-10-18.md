# 2026-10-18

## Today's Focus: Relocating Oracle Indexes to the Correct Tablespace

## Category: Oracle / Database Maintenance / Production Change

### Problem Description

The DBA team reported that some indexes in the production Oracle database 
were incorrectly stored in the data tablespace instead of the designated 
index tablespace. To comply with database storage standards, these indexes 
needed to be relocated to the correct tablespace.

### Troubleshooting Steps

#### Step 1 - Identify Indexes in the Wrong Tablespace

Queried the Oracle data dictionary to identify indexes stored in the data tablespace:

```sql
SELECT index_name, tablespace_name, owner 
FROM all_indexes
WHERE owner = USER
AND tablespace_name LIKE '%\_DATA' ESCAPE '\'
```

**Finding**: Several indexes were stored in the data tablespace instead of the 
designated index tablespace.

#### Step 2 - Relocate Indexes Using ONLINE REBUILD

Prepared individual SQL statements for each affected index and executed them 
during the production change window.

```sql
ALTER INDEX TABLE_OWNER.INDEX_NAME_1
REBUILD ONLINE TABLESPACE TABLE_OWNER_IDX;
```

The `ONLINE` option allowed most application read and write operations to 
continue during the index rebuild.

#### Step 3 - Verify Index Tablespace Allocation

After the changes, queried the Oracle data dictionary again:

```sql
SELECT index_name, tablespace_name, owner 
FROM all_indexes
WHERE owner = USER
AND tablespace_name LIKE '%\_DATA' ESCAPE '\'
```

**Result**: No indexes were returned within the scope of the query.

Also verified the tablespace allocation of the relocated indexes:

```sql
SELECT index_name, tablespace_name, owner 
FROM all_indexes 
WHERE owner = USER
AND tablespace_name LIKE '%\_IDX' ESCAPE '\'
```

### Root Cause

Some indexes were created without explicitly specifying the 
designated index tablespace in the database deployment scripts. 
As a result, Oracle placed these indexes in the schema's default data 
tablespace, while indexes with an explicitly defined TABLESPACE clause 
were correctly created in the index tablespace.

### Resolution

- Identified indexes stored in the incorrect data tablespace.
- Executed individual `ALTER INDEX REBUILD ONLINE` statements. 
Relocated the affected indexes to the designated index tablespace without 
stopping application services.
- Verified that no indexes remained in the data tablespace within the scope
of the validation query.

### Lessons Learned

#### Why should indexes be stored in a separate tablespace?

Separating indexes from table data provides several benefits:

- **Performance**: If index and data tablespaces use different physical 
storage resources, separating them may reduce I/O contention and improve 
query performance, especially under heavy workloads.

- **Storage Management**: Allows DBAs to independently monitor and manage 
space usage, storage allocation, and growth for indexes and table data.

- **Maintenance**: Simplifies index rebuilding, relocation, and other 
maintenance operations without affecting the storage organization of table data.

However, separating indexes into different tablespaces does not automatically 
improve performance if they share the same underlying storage resources.

#### How can similar issues be prevented?

- Explicitly specify the designated TABLESPACE when creating indexes.
- Review database deployment scripts before production changes.
