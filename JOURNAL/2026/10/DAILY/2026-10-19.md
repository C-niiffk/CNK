# 2026-10-19

## Today's Focus: Troubleshooting Client IP Forwarding Through F5 Load Balancer

## Category: Networking / F5 / Gateway

### Problem Description

During API Gateway troubleshooting, the Gateway received the F5 
Load Balancer IP instead of the original client IP when requests 
passed through F5. Further investigation revealed that Source Network 
Address Translation (SNAT) was configured on F5 to handle traffic between 
clients and backend servers within the same subnet.

### Troubleshooting Steps

#### Step 1 - Compare Direct and Load-Balanced Access

Tested requests from a VM using two different network paths.

**Path A: Client → API Gateway**

```text
Remote IP: CLIENT_IP
X-Forwarded-For: Not present
```

**Path B: Client → F5 → API Gateway**

```text
Remote IP: F5_IP
X-Forwarded-For: Not present
```

**Finding**: When requests passed through F5, the Gateway received 
the load balancer's IP instead of the original client IP.

#### Step 2 - Investigate F5 SNAT Configuration

Further investigation revealed that SNAT was enabled on F5 for 
traffic between clients and backend servers within the same subnet. 
Without SNAT, the backend server could send response packets directly 
to the client because both were on the same subnet, bypassing F5. 
This could cause asymmetric routing and connection failures.

With SNAT enabled, F5 replaced the original client source IP with 
its own SNAT address, ensuring that response traffic returned through F5. 
However, the Gateway could no longer identify the original client 
through the connection's source IP.

#### Step 3 - Investigate X-Forwarded-For

To preserve the original client IP, F5 needed to 
be configured to insert the `X-Forwarded-For` header:

```text
Remote IP: F5_IP
X-Forwarded-For: CLIENT_IP
```

This allows the Gateway to obtain the original client IP from a 
trusted forwarding header while SNAT maintains the correct return path.

### Root Cause

The issue was caused by F5 SNAT configuration combined with the absence 
of client IP forwarding through `X-Forwarded-For`.

SNAT was required for the same-subnet network topology to prevent 
backend responses from bypassing F5. However, source address translation 
replaced the original client IP with the F5 SNAT address, and the Gateway 
did not receive an HTTP header containing the original client IP.

### Resolution

- Confirmed that SNAT was required for same-subnet traffic.
- Configured F5 to insert the `X-Forwarded-For` header to preserve the original client IP.

### Lessons Learned

#### How does X-Forwarded-For solve the problem?

`X-Forwarded-For` is an HTTP header commonly used to preserve client IP information across proxies.
The Gateway can retrieve this information when the header is supplied by a trusted proxy.
However, X-Forwarded-For does not replace SNAT or solve routing asymmetry by itself. 
It only preserves client IP information at the HTTP layer.

#### Can X-Forwarded-For always be trusted?

No. Clients can supply their own X-Forwarded-For values. Applications should
only trust forwarding information that has been validated or rewritten by explicitly trusted proxies.

#### Why is SNAT required when clients and servers are in the same subnet?

Without SNAT, a backend server may respond directly to a client on the same subnet, 
bypassing the load balancer. SNAT ensures that return traffic passes through F5, 
maintaining a symmetric network path.
