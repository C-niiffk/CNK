# 2026-10-29

## Today's Focus: Automatic Startup for VM Applications

## Category: Linux / systemd / Podman

### Background

VM applications can start automatically in several ways, 
depending on whether they run directly as JAR files or inside Podman containers.

### 1. Direct Java Application

A JAR deployed directly on the VM can be managed with a system-level systemd service:

```ini
# File: /etc/systemd/system/demo-app.service
[Unit]
Description=Demo Java Application
After=network-online.target
Wants=network-online.target

[Service]
Type=simple
User=appuser
WorkingDirectory=/opt/demo
ExecStart=/usr/bin/java -jar /opt/demo/app.jar
Restart=on-failure
RestartSec=5s

[Install]
WantedBy=multi-user.target
```

Enable and start the service:

```bash
sudo systemctl daemon-reload
sudo systemctl enable --now demo-app.service
```

Check the service and logs:

```bash
sudo systemctl status demo-app.service
sudo journalctl -u demo-app.service -f
```

### 2. Podman Containers with `podman-restart.service`

For rootless Podman, the container can be configured with a restart policy:

```bash
podman run -d \
  --name demo-container \
  --restart=always \
  example/demo:1.0
```

Enable the user-level Podman restart service:

```bash
loginctl enable-linger appuser
systemctl --user enable podman-restart.service
systemctl --user status podman-restart.service
```

- `enable-linger` allows the user’s systemd manager to start during VM boot even when the user has not logged in
- `podman-restart.service` restores containers that have a suitable restart policy.
  It is a general recovery service and does not require a separate service file for every container.

### 3. Podman Container with an Individual systemd Service

A specific container can also have its own user-level systemd service:

```text
~/.config/systemd/user/container-demo.service
```

The service can be generated by Podman or created manually. A generated service may contain:

```ini
[Service]
Restart=always
ExecStart=/usr/bin/podman start demo-container
ExecStop=/usr/bin/podman stop -t 10 demo-container
```

Enable it with:

```bash
systemctl --user daemon-reload
systemctl --user enable --now container-demo.service
```

This method provides individual control:

```bash
systemctl --user status container-demo.service
systemctl --user restart container-demo.service
journalctl --user -u container-demo.service
```

### 4. Quadlet

Quadlet uses a `.container` file to describe a Podman container and generate a systemd service:

```ini
# File: ~/.config/containers/systemd/demo.container
[Container]
Image=example/demo:1.0
ContainerName=demo-container
PublishPort=8080:8080

[Service]
Restart=on-failure

[Install]
WantedBy=default.target
```

### 5. Why Not Use `crontab`?

`crontab` can run a command at boot:

```cron
@reboot /opt/demo/bin/start.sh
```

However, it is mainly designed for scheduled jobs. It does not provide 
the same service management features as systemd:
- Automatic restart after an unexpected failure
- Service status and exit-code tracking
- Startup dependencies
- Centralized logs

Therefore, `crontab` is suitable for simple scheduled tasks or a basic `@reboot` script,
while long-running JAR and Podman services are better managed by systemd.
