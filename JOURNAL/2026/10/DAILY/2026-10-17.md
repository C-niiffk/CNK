# 2026-10-17

## Today's Focus: Troubleshooting Nacos Raft Leader Election Failures

## Category: Nacos / Raft/ Derby / Production Troubleshooting

### Problem Description

A production alert reported that one GRDC Pod in Site B had a 
Prometheus up status of 0. GRDC is a customized Nacos-based
service deployed as a cluster using embedded Derby storage 
and Raft-based consensus in Site B.

Further investigation revealed:

- Application configurations were not displayed in the Nacos UI
- The Service List was empty in the Nacos UI
- Configuration queries returned HTTP 500 and timeout errors
- Restarting the GRDC pods did not resolve the issue

#### Troubleshooting Steps

#### Step 1 - Check GRDC Pod Status and Logs

```bash
oc get pods -n NAMESPACE
oc logs POD_NAME -n NAMESPACE --tail=300
```

**Finding**: GRDC processes were not necessarily stopped, but configuration
queries and cluster coordination were failing.

#### Step 2 - Investigate Raft Leader Election

The logs reported:

```text
ERROR ReadIndex has error: No leader at term 7980, go to Leader read
```

Raft leader changes were also observed.

**Finding**: GRDC experienced leader election or leader availability problems,
accompanied by gRPC and Raft ReadIndex timeouts.

#### Step 3 - Investigate Database Query Timeouts

The application logs repeatedly reported:

```text
ERROR An exception occurred during the query operation: java.util.concurrent.TimeoutException
```

GRDC uses embedded Derby storage. According to the existing implementation, 
some data operations depend on Raft-based consistency confirmation.
During the leader election failure, these operations could not complete 
within the expected timeout.

### Root Cause

The incident involved repeated Raft leader election and ReadIndex timeouts. 
Potential contributing factors included embedded Derby database performance 
limitations and the consistency confirmation mechanism during leader transitions. 
These timeouts caused GRDC queries to become blocked or fail, affecting 
configuration management and service discovery.
Network instability was suspected to have contributed to the leader instability

### Resolution

#### Immediate Recovery

Ordinary Pod restarts did not restore GRDC.

The recovery procedure was:

1. Backed up the persistent data/protocol directory
2. Removed the existing protocol directory
3. Restarted the GRDC pods
4. Verified that the GRDC cluster started successfully
5. Confirmed that application configurations and registered services
   were displayed normally

#### Long-Term Improvement

- Plan to migrate GRDC configuration storage from 
embedded Derby to Oracle
- Review Raft leader election stability and timeout behavior

### Lessons Learned

#### Why can a running Pod still be unavailable?

A running process does not guarantee that its internal services can respond successfully.
Raft consensus failures and blocked queries may cause health checks or monitoring requests to time out.

#### Why did restarting the Pods fail?

The persistent Raft protocol state remained unchanged after an ordinary restart, 
so the cluster continued to encounter initialization and leader availability errors.
