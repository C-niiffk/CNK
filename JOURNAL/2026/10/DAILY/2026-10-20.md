# 2026-10-20

## Today's Focus: JDK 8 to JDK 17 Upgrade - Code Changes and Compatibility Issues

## Background

The upgrade from JDK 8 to JDK 17 also involved upgrading to Spring Boot 3.x 
and Spring Framework 6.x, along with updates to related libraries.

## Selected Code and Configuration Changes

The following table highlights some of the changes made 
during the upgrade. It is not an exhaustive list.

These changes covered framework compatibility, API documentation, 
HTTP clients, and optional code modernization. 
Not every change was required by JDK 17 itself.

| Area                       | Previous implementation                   | Updated implementation                                               | Notes                                                                                                           |
|----------------------------|-------------------------------------------|----------------------------------------------------------------------|-----------------------------------------------------------------------------------------------------------------|
| API model annotation       | `@ApiModel(value = "...")`                | `@Schema(name = "...")`                                              | Use `description` for descriptive text.                                                                         |
| API property annotation    | `@ApiModelProperty(value = "...")`        | `@Schema(description = "...")`                                       | Preserves the property description.                                                                             |
| API operation annotation   | `@ApiOperation(value = "...")`            | `@Operation(summary = "...")`                                        | Migrates operation documentation.                                                                               |
| Swagger imports            | `io.swagger.annotations.*`                | `io.swagger.v3.oas.annotations.*` and relevant subpackages           | Adopts OpenAPI 3 annotations.                                                                                   |
| Java EE imports            | Relevant `javax.*` packages               | Corresponding `jakarta.*` packages                                   | Replace Java EE imports used by the upgraded framework with their Jakarta equivalents. Retain Java SE packages. |
| String formatting          | `String.format(format, args)`             | `format.formatted(args)`                                             | Optional modernization; the original API remains supported.                                                     |
| Path construction          | `Paths.get(...)`                          | `Path.of(...)`                                                       | Optional modernization; the original API remains supported.                                                     |
| HTTP method access         | `getMethodValue()`                        | `getMethod()`                                                        | Returns an `HttpMethod` rather than a String.                                                                   |
| Serialization declarations | Fields or methods without `@Serial`       | Apply `java.io.Serial` where appropriate                             | Optional compiler-assisted checking of serialization declarations.                                              |
| Empty-value checks         | Selected `StringUtils.isEmpty(...)` calls | `ObjectUtils.isEmpty(...)` or string-specific checks                 | Preserve the intended validation behavior.                                                                      |
| Apache HTTP client         | Relevant `org.apache.http.*` classes      | Corresponding `org.apache.hc.*` classes                              | Part of the HttpClient 4-to-5 upgrade; additional API changes may be required.                                  |
| Spring MVC configuration   | `extends WebMvcConfigurerAdapter`         | `implements WebMvcConfigurer`                                        | Replaces the deprecated adapter.                                                                                |
| API documentation metadata | Previous documentation endpoint           | Metadata pointing to the OpenAPI 3 endpoint in `bootstrap-nacos.yml` | The default springdoc endpoint is /v3/api-docs.                                                                 |

## Compatibility Issues

### 1. IBM MQ Connection Failure

#### Problem

The application connected successfully to IBM MQ before the upgrade. 
After upgrading to JDK 17 and Spring Boot 3.x, the JMS connection 
failed during startup, preventing normal service operation.

The application repeatedly reported connection recovery attempts:

```text
Could not refresh JMS Connection for destination '<QUEUE_NAME>'
Retrying using FixedBackOff ...

IBM MQ call failed with compcode '2'
reason '2035' ('MQRC_NOT_AUTHORIZED')
```

The application ran on OpenShift and used IBM MQ 9.x, an IBM 
MQ 9.x client library, and the following Spring Boot integration:

```xml
<dependency>
    <groupId>com.ibm.mq</groupId>
    <artifactId>mq-jms-spring-boot-starter</artifactId>
</dependency>
```

Neither the application nor the queue manager was configured to 
require an application-supplied username and password.

#### Investigation

The queue manager error log, `AMQERR.LOG`, showed the following message:

```text
AMQ9557E: Queue Manager User ID initialization failed
for '<CONTAINER_OS_USER>'.
```

The reported identity matched the operating-system user associated 
with the application container. This showed that the absence of 
explicitly configured credentials did not mean that MQ ignored client identity. 
The queue manager was attempting to initialize a user identity, and reason 
code `2035` indicated an authorization-related failure.

#### Resolution

A dedicated IBM MQ configuration class was introduced to construct the 
`MQConnectionFactory` explicitly. The MQ server host and port were configured separately, 
together with the required connection properties.

After this change, the application connected successfully.


### 2. SkyWalking Agent and Spring Cloud Gateway

#### Problem

After the Gateway was upgraded to JDK 17, Spring Boot 3.x, 
and Spring Framework 6.x, it continued to use a SkyWalking 8.x agent.

Although the Gateway started, its monitoring data was unavailable 
in the SkyWalking UI. The Gateway logs reported the following instrumentation error:

```text
ERROR reactor-http-epoll-3 InstMethodsInter:
class[class org.springframework.web.reactive.DispatcherHandler]
before method[handle] intercept failure
```

#### Investigation

The Gateway used Spring WebFlux 6.x after the upgrade, but the installed SkyWalking 
plugin was designed for Spring WebFlux 5.x.

The failure occurred when the agent intercepted `DispatcherHandler.handle`, 
indicating a compatibility issue between the instrumentation and the upgraded framework.

#### Resolution

The SkyWalking agent was upgraded to a compatible 9.x release for the upgraded Gateway.
The agent distribution and activated plugins must be treated as one compatible set. 
Plugin selection must match Spring WebFlux 6.x, and incompatible plugins from the old 
installation should not be carried into the replacement agent.
