## Today's Focus: RHEL Production Troubleshooting

## Scenario 1: A systemd Service Fails to Start

### Problem

A Java application managed by systemd fails to start after a configuration change.

### Step 1: Check Service Status

```bash
sudo systemctl status demo-app.service --no-pager -l
```

Example output:

```text
● demo-app.service - DEMO Application
     Loaded: loaded (/etc/systemd/system/demo-app.service)
     Active: failed (Result: exit-code)

Main process exited, code=exited, status=1/FAILURE
```

The service is in the `failed` state, and the main process exited with a non-zero status.

### Step 2: Inspect Service Logs

```bash
sudo journalctl -u demo-app.service -n 100 --no-pager
```

Example output:

```text
java.nio.file.NoSuchFileException:
/opt/demo/config/application.yml
```

The application cannot locate its configuration file.

### Step 3: Inspect the systemd Configuration

```bash
sudo systemctl cat demo-app.service

sudo systemctl show demo-app.service \
  -p ExecStart \
  -p WorkingDirectory \
  -p User
```

Example output:

```text
ExecStart={ path=/usr/bin/java ; argv[]=/usr/bin/java -Xms2g -Xmx4g -jar /opt/demo/demo-app.jar ; ... }
WorkingDirectory=/opt/demo
User=demo
```

Check the required file:

```bash
ls -l /opt/demo/config/application.yml

namei -l /opt/demo/config/application.yml
```

The investigation reveals that the configuration file is missing 
or that one of its parent directories is inaccessible to the service user.

### Root Cause

The application configuration path is incorrect or the required 
file was not deployed.

### Resolution

Restore the configuration file from a verified deployment 
artifact or correct the path in the systemd unit.

If the unit file was changed:

```bash
sudo systemctl daemon-reload
```

Restart the application:

```bash
sudo systemctl restart demo-app.service
```

Verify:

```bash
systemctl is-active demo-app.service

sudo journalctl -u demo-app.service -n 30 --no-pager
```

Expected output:

```text
active
```

## Scenario 2: Java Application Terminated by the OOM Killer

### Problem

A Java application unexpectedly stops. The service logs do not 
contain a normal shutdown message.

### Step 1: Check Service Status

```bash
sudo systemctl status demo-app.service --no-pager -l
```

Example output:

```text
Active: failed (Result: signal)
Main process exited, code=killed, status=9/KILL
```

The Java process was terminated by SIGKILL.

### Step 2: Check Kernel Logs for OOM Events

```bash
sudo journalctl -k --since "1 hour ago" --no-pager \
  | grep -Ei 'out of memory|oom-kill|killed process'
```

Example output:

```text
oom-kill: constraint=CONSTRAINT_MEMCG
Memory cgroup out of memory: Killed process 2451 (java)
```

`CONSTRAINT_MEMCG` indicates that the OOM event was associated 
with a memory cgroup limit.

If the logs indicate a global OOM instead, investigate overall 
host memory pressure.

### Step 3: Check Host Memory Usage

```bash
free -h
```

Example output:

```text
               total   used   free   shared  buff/cache  available
Mem:            16Gi   14Gi  500Mi    200Mi       1.5Gi      1.1Gi
Swap:            2Gi  1.8Gi  200Mi
```

Available memory is low, and swap usage is high.

Check memory pressure over time:

```bash
vmstat 1 5
```

Sustained non-zero `si` and `so` values, together with 
low available memory, may indicate host-level memory 
pressure and active swapping.

### Step 4: Check systemd Memory Limits

```bash
systemctl show demo-app.service \
  -p MemoryMax \
  -p MemoryHigh
```

Example output:

```text
MemoryHigh=6442450944
MemoryMax=8589934592
```

### Step 5: Inspect Java Process Memory Usage

If the Java process has restarted and is running:

```bash
PID=$(pgrep -f 'demo-app.jar' | head -n 1)

sudo grep -E 'VmRSS|VmSize|Threads' \
  /proc/"$PID"/status
```

Example output:

```text
VmSize: 10500000 kB
VmRSS:   6500000 kB
Threads:      180
```

Interpretation:

- `VmSize`: Approximately 10 GiB of virtual address space.
- `VmRSS`: Approximately 6.2 GiB of resident memory.
- `Threads`: 180 threads.

### Step 6: Inspect cgroup Memory Usage and OOM Events

Identify the service's cgroup:

```bash
systemctl show demo-app.service -p ControlGroup
```

Example output:

```text
ControlGroup=/system.slice/demo-app.service
```

Inspect the memory files:

```bash
CGROUP=$(systemctl show -P ControlGroup demo-app.service)

sudo cat "/sys/fs/cgroup${CGROUP}/memory.current"

sudo cat "/sys/fs/cgroup${CGROUP}/memory.max"

sudo cat "/sys/fs/cgroup${CGROUP}/memory.events"
```

Example output:

```text
# memory.current
7900000000

# memory.max
8589934592

# memory.events
low 0
high 125
max 18
oom 3
oom_kill 1
oom_group_kill 0
```

Interpretation:

| Metric           | Meaning                                                   |
|------------------|-----------------------------------------------------------|
| `memory.current` | Current memory usage charged to the cgroup                |
| `memory.max`     | Maximum cgroup memory limit                               |
| `high`           | Number of memory-high events                              |
| `max`            | Number of times memory usage reached the maximum boundary |
| `oom`            | Number of recorded OOM conditions                         |
| `oom_kill`       | Number of processes killed by an OOM Killer               |

The service's cgroup memory usage is approaching its 8 GiB limit, and OOM events have been recorded.

### Step 7: Check JVM Heap Configuration

```bash
ps -ef | grep 'java'
```

Example output:

```text
java -Xms4g -Xmx8g -jar demo-app.jar
```

The JVM maximum heap is configured to 8 GiB, 
equal to the service's `MemoryMax`.

This configuration leaves no explicit headroom 
within the 8 GiB cgroup limit for other JVM memory usage, including:

- Metaspace
- Thread stacks
- Direct buffers
- Native memory
- JVM internal structures

If the application is running, inspect JVM heap information:

```bash
jcmd "$PID" GC.heap_info
```

JVM heap information is available for comparison 
with the configured maximum heap size.

### Root Cause

For this example, the Java application is configured with `-Xmx8g`, while the systemd service has a `MemoryMax` limit of 8 GiB.

During batch processing, the combined JVM heap and native memory consumption exceeds the cgroup memory limit.

The kernel triggers a memory cgroup OOM event and terminates the Java process.

### Resolution

1. Review JVM heap and native memory requirements.
2. Reduce the maximum heap size to leave sufficient memory for JVM overhead and other allocations.
3. Investigate excessive object allocation, memory leaks, and batch-processing memory consumption.
4. Review the systemd memory limits and host capacity.
5. Apply configuration changes through the approved deployment process.

If the systemd unit configuration was changed:

```bash
sudo systemctl daemon-reload
```

Restart the application:

```bash
sudo systemctl restart demo-app.service
```

### Verification

Check service status:

```bash
systemctl is-active demo-app.service
```

Expected output:

```text
active
```

Check host memory:

```bash
free -h

vmstat 1 5
```

Check cgroup memory usage and OOM events:

```bash
CGROUP=$(systemctl show -P ControlGroup demo-app.service)

sudo cat "/sys/fs/cgroup${CGROUP}/memory.current"

sudo cat "/sys/fs/cgroup${CGROUP}/memory.events"
```

Check for new kernel OOM messages:

```bash
sudo journalctl -k --since "10 minutes ago" --no-pager \
  | grep -Ei 'out of memory|oom-kill|killed process'
```

The application remains active, cgroup memory usage 
stays within the configured limit, and no new OOM events occur.

## Scenario 3: Disk Usage Is 100%, but No Large Files Are Found

### Problem

A filesystem reports 100% disk usage, but the visible 
directory sizes do not explain the consumed space.

### Step 1: Check Filesystem Usage

```bash
df -h
```

Example output:

```text
Filesystem          Size  Used Avail Use% Mounted on
/dev/mapper/rhel-var  20G   20G     0 100% /var
```

`/var` has no available disk space

### Step 2: Check Directory Sizes

```bash
sudo du -xhd1 /var | sort -h
```

Example output:

```text
200M    /var/log
500M    /var/cache
1.2G    /var/lib
2.0G    /var
```

Visible files account for only a small portion of the filesystem usage.

### Step 3: Check Inode Usage

```bash
df -i /var
```

Example output:

```text
Filesystem          Inodes  IUsed  IFree IUse% Mounted on
/dev/mapper/rhel-var  10M    120K   9.8M     2% /var
```

Inodes are not exhausted.

### Step 4: Identify Deleted but Open Files

```bash
sudo lsof +L1
```

Example output:

```text
COMMAND  PID   USER  FD   TYPE  SIZE/OFF  NLINK NAME
java     2451  demo   12w  REG   18G       0     /var/log/demo/app.log (deleted)
```

The investigation reveals that a Java process still holds an open file descriptor
to a deleted 18 GB log file.

### Root Cause

A large log file was deleted while the application was still writing to it.
The file remained open, preventing the filesystem from reclaiming the disk space.

### Resolution

Identify the affected process and assess the operational impact.

If a controlled application restart is safe:

```bash
sudo systemctl restart demo-app.service
```

Verify:

```bash
df -h /var

sudo lsof +L1
```

Expected result:

```text
Filesystem          Size  Used Avail Use% Mounted on
/dev/mapper/rhel-var  20G  2.0G   18G  10% /var
```

## Scenario 4: Application Cannot Connect to a Remote Database

### Problem

A Java application running on RHEL cannot connect to an Oracle database.

Example application error:

```text
java.sql.SQLRecoverableException:
IO Error: The Network Adapter could not establish the connection
```

### Step 1: Verify DNS Resolution

```bash
getent hosts db.example.com
```

Example output:

```text
10.20.30.40 db.example.com
```

If the hostname does not resolve, investigate DNS configuration:

```bash
cat /etc/resolv.conf

resolvectl status
```

### Step 2: Verify Routing

```bash
ip route get 10.20.30.40
```

Example output:

```text
10.20.30.40 via 10.20.0.1 dev ens192 src 10.20.0.15
```

The host has a route to the database network.

### Step 3: Test TCP Connectivity

```bash
nc -vz -w 5 db.example.com 1521
```

Successful example:

```text
Connection to db.example.com 1521 port [tcp/*] succeeded!
```

Failure example:

```text
nc: connect to db.example.com port 1521 (tcp) timed out
```

A timeout suggests that the connection was not completed, 
but does not uniquely identify a firewall problem.

### Step 4: Inspect Local Firewall Rules

```bash
sudo firewall-cmd --state

sudo firewall-cmd --list-all

sudo nft list ruleset
```

No local rule is unexpectedly blocking the required outbound connection or return traffic.

### Step 5: Capture Network Traffic

```bash
sudo tcpdump -ni any \
  'host 10.20.30.40 and tcp port 1521'
```

Possible output:

```text
10.20.0.15.45320 > 10.20.30.40.1521: Flags [S]
10.20.0.15.45320 > 10.20.30.40.1521: Flags [S]
10.20.0.15.45320 > 10.20.30.40.1521: Flags [S]
```

Repeated SYN packets are sent, but no SYN-ACK or RST is observed.
This indicates that the TCP handshake did not complete from the 
client's perspective. The root cause could involve network filtering, 
routing, or the destination.

### Root Cause

For this example, a network firewall rule blocks TCP port 1521 
between the application server and database.

### Resolution

Confirm the intended source, destination, port, and approved network path.
Request the appropriate firewall rule change.

### Verification

```bash
nc -vz -w 5 db.example.com 1521
```

Expected output:

```text
Connection to db.example.com 1521 port [tcp/*] succeeded!
```

## Scenario 5: High Load Average but Low CPU Utilisation

### Problem

A RHEL server has a load average of 20, but CPU utilization remains relatively low.
The application responds slowly, especially during file operations.

### Step 1: Check Load Average

```bash
uptime
```

Example output:

```text
20:15:10 up 30 days,  2 users,
load average: 20.50, 18.20, 15.30
```

The load average is consistently high.

### Step 2: Check CPU and I/O Wait

```bash
vmstat 1 5
```

Example output:

```text
 r  b   swpd   free   buff  cache  si so   bi    bo   in   cs us sy id wa st
 1 18      0  50000  30000 200000  0  0  500  1200  500 1000  5  3 35 57  0
```

Important columns:

- `r`: Runnable tasks
- `b`: Tasks blocked waiting for I/O
- `id`: CPU idle percentage
- `wa`: I/O wait percentage

Many tasks are blocked, and CPU I/O wait is elevated.

### Step 3: Check Disk Performance

```bash
iostat -xz 1 5
```

Example output:

```text
Device   r/s   w/s   await  aqu-sz  %util
sda      100   250   85.0    20.0   99.5
```

The disk has high average I/O latency and a substantial queue.

### Step 4: Identify Affected Processes

```bash
pidstat -d 1 5
```

Example output:

```text
UID    PID   kB_rd/s   kB_wr/s  iodelay  Command
1001   2451  10240.0   20480.0      150  java
```

The Java process generates substantial disk I/O or experiences I/O delays.

Check tasks in uninterruptible sleep:

```bash
ps -eo pid,ppid,stat,wchan:30,comm \
  | awk '$3 ~ /^D/'
```

### Root Cause

For this example, heavy disk I/O causes application threads to wait for storage operations.
The result is high load average despite relatively low CPU utilization.

### Resolution

Investigate the source of excessive I/O:

- Large batch file processing
- Excessive application logging
- Backup or scheduled jobs
- Storage latency or contention
- Filesystem or underlying disk errors

Possible corrective actions include:

- Rescheduling competing batch jobs.
- Reducing unnecessary synchronous I/O.
- Optimising file processing and logging.
- Reviewing storage throughput and latency.
- Increasing storage capacity or performance where justified.

### Verification

```bash
uptime

vmstat 1 5

iostat -xz 1 5

pidstat -d 1 5
```

Blocked tasks and I/O latency decrease, application response times 
improve, and load average gradually returns to its normal baseline.

## Scenario 6: Sustained High CPU Usage on a Linux Server

### Problem

A Java application running on RHEL experiences slow response times, 
while the server's CPU utilization remains above 95%.

### Step 1: Check CPU Utilisation

```bash
top
```

Example output:

```text
%Cpu(s): 85.0 us, 10.0 sy, 3.0 id, 2.0 wa
```

Confirm whether CPU usage remains high:

```bash
vmstat 1 5
```

User CPU utilization remains high (`us = 85%`), while idle time is 
low (`id = 3%`), indicating that the CPU is primarily occupied with 
application processing rather than I/O waiting.

### Step 2: Identify the Process Consuming CPU

```bash
ps -eo pid,ppid,comm,%cpu,%mem --sort=-%cpu | head -15
```

Example output:

```text
PID    PPID  COMMAND  %CPU  %MEM
2451      1  java     380.0  45.0
3102      1  nginx      2.5   1.2
```

The Java process (PID 2451) consumes approximately 380% CPU, 
equivalent to roughly 3.8 CPU cores.

### Step 3: Identify High-CPU Threads

```bash
top -H -p 2451

pidstat -t -u -p 2451 1 5
```

Example output:

```text
TID    %CPU   Command
2510   99.0   java
2511   98.5   java
2512   95.0   java
```

Several Java threads are consuming nearly one CPU core each.

### Step 4: Analyze Java Thread Stacks

Convert the Linux Thread ID to hexadecimal:

```bash
printf '%x\n' 2510
```

Expected output:

```text
9ce
```

Collect a Java thread dump:

```bash
jcmd 2451 Thread.print -l > /tmp/java-threads.txt
```

Find the corresponding thread:

```bash
grep -A 35 'nid=0x9ce' /tmp/java-threads.txt
```

Example output:

```text
"worker-1" #45 prio=5 os_prio=0
   nid=0x9ce runnable

   java.lang.Thread.State: RUNNABLE
       at com.example.batch.FileProcessor.process(FileProcessor.java:128)
       at com.example.batch.BatchService.execute(BatchService.java:65)
```

The high-CPU thread is repeatedly executing `FileProcessor.process()`.

### Step 5: Check JVM Garbage Collection

```bash
jstat -gcutil 2451 1000 5
```

Example output:

```text
 S0    S1     E      O      M     YGC    YGCT    FGC   FGCT
 0.0   45.0   85.0   72.0   95.0   150    3.2     2    0.5
 0.0   45.0   92.0   72.0   95.0   151    3.3     2    0.5
```

GC counters and cumulative GC time can be compared across 
samples to determine whether garbage collection is contributing to CPU usage.

### Root Cause

For this example, the Java batch application contains an inefficient processing loop that repeatedly scans a large file, resulting in excessive CPU consumption.

Multiple worker threads execute the same CPU-intensive operation concurrently, causing sustained high CPU utilization and increased application response times.

### Resolution

1. Optimize the file-processing algorithm to eliminate unnecessary repeated scans.
2. Review thread concurrency and batch-processing configuration.
3. Use Java Flight Recorder to verify CPU-intensive code paths.
4. Perform load testing before deploying the change.

### Verification

```bash
top -p 2451

pidstat -u -p 2451 1 5

vmstat 1 5
```

CPU utilization decreases to its normal baseline, application 
response times improve, and batch processing completes successfully 
without excessive resource consumption.

## General Troubleshooting Methodology

For Linux production incidents, follow a consistent investigation process:

```text
1. Identify the symptoms
        |
        v
2. Check system and service status
        |
        v
3. Collect logs and metrics
        |
        v
4. Isolate the affected component
        |
        v
5. Form and validate a root-cause hypothesis
        |
        v
6. Apply an approved corrective action
        |
        v
7. Verify service recovery
        |
        v
8. Implement preventive measures
```
