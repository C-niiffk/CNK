# Today's Focus: Load Balancer

## Application Load Balancer

### How It Works

Application Load Balancer operates at Layer 7 and distributes 
HTTP/HTTPS requests across registered backend targets.

### Common Use Cases

- HTTP/HTTPS load balancing.
- Path-based routing.
- Host-based routing.
- TLS termination.
- Health checks and automatic target selection.
- Routing multiple microservices through one entry point.

### Troubleshooting Scenarios

### Scenario 1: Requests Are Routed to the Wrong Backend

**Problem**

A bank hosts Payment Service and Customer Service behind the 
same ALB. However, requests intended for Payment Service 
are routed to Customer Service.

Example:

```text
https://bank.example.com/payment
```

The request unexpectedly reaches Customer Service.

**Investigation**

**Step 1: Check ALB listener rules.**

```bash
aws elbv2 describe-rules \
  --listener-arn "$LISTENER_ARN" \
  --query 'Rules[].{Priority:Priority,Conditions:Conditions,Actions:Actions}' \
  --output json
```

Possible output:

```text
[
  {
    "Priority": "10",
    "Conditions": [
      {
        "Field": "path-pattern",
        "Values": ["/payment/*"]
      }
    ],
    "Actions": [
      {
        "Type": "forward",
        "TargetGroupArn": "customer-tg-arn"
      }
    ]
  },
  {
    "Priority": "20",
    "Conditions": [
      {
        "Field": "path-pattern",
        "Values": ["/payment/*"]
      }
    ],
    "Actions": [
      {
        "Type": "forward",
        "TargetGroupArn": "payment-tg-arn"
      }
    ]
  }
]
```

Review the path-pattern, host-header conditions, rule priority and forwarding action.

**Step 2: Check Target Group associations.**

```bash
aws elbv2 describe-target-groups \
  --load-balancer-arn "$ALB_ARN"
```

Expected:

```text
TargetGroups:
  - TargetGroupName: payment-tg
    TargetGroupArn: payment-tg-arn

  - TargetGroupName: customer-tg
    TargetGroupArn: customer-tg-arn
```

Confirm that the listener rule forwards requests to the correct Target Group.

**Step 3: Test the application routing.**

```bash
curl -i https://bank.example.com/payment
```

Possible output:

```text
HTTP/2 200
Content-Type: application/json

{"service":"customer"}
```

The HTTP request succeeds, but the response identifies the wrong backend service.

**Possible Causes**

- Incorrect path-pattern condition.
- Incorrect host-header condition.
- Listener rule priority is incorrect.
- A request matches an earlier rule unexpectedly.
- The rule forwards traffic to the wrong Target Group.

**Resolution**

Correct the listener rule conditions, priority or Target Group association.

Retest:

```bash
curl -i https://bank.example.com/payment
```

Expected:

```text
HTTP/2 200

{"service":"payment"}
```

## Network Load Balancer

### How It Works

Network Load Balancer operates at Layer 4 and distributes
TCP, UDP and TLS traffic across registered targets.

### Common Use Cases

- TCP-based applications.
- UDP-based services.
- TLS traffic distribution.
- Applications requiring static IP addresses.
- Preserving original client source IP addresses.
- High-performance and low-latency network connections.
- AWS PrivateLink services.

### Troubleshooting Scenarios

### Scenario 1: Backend Application Cannot Identify the Original Client IP

**Problem**

An application behind NLB records the NLB private IP instead of the original client IP.

Example application log:

```text
Client IP: 10.42.1.100
```

However, the actual client IP should be:

```text
203.0.113.25
```

**Investigation**

**Step 1: Check Target Group attributes.**

```bash
aws elbv2 describe-target-group-attributes \
  --target-group-arn "$TG_ARN"
```

Possible output:

```text
Key: preserve_client_ip.enabled
Value: false

Key: proxy_protocol_v2.enabled
Value: false
```

Client IP preservation is disabled.

**Step 2: Check Target Group protocol and target type.**

```bash
aws elbv2 describe-target-groups \
  --target-group-arns "$TG_ARN"
```

Expected fields:

```text
TargetType: ip
Protocol: TCP
Port: 8080
```

For TCP/TLS IP target groups, client IP preservation is disabled by default.

**Step 3: Review application access logs.**

```bash
sudo tail -n 20 /var/log/demo-app/access.log
```

Possible output:

```text
2026-11-16 10:30:00
client_ip=10.42.1.100
```

The backend records the NLB node address instead of the original client IP.

**Possible Causes**

- Client IP preservation is disabled.
- Target type and protocol have different default preservation behavior.
- Backend application does not parse Proxy Protocol v2 correctly.

**Resolution**

For TCP/TLS IP target groups, enable client IP preservation 
if the network architecture supports it.

Example:

```bash
aws elbv2 modify-target-group-attributes \
  --target-group-arn "$TG_ARN" \
  --attributes Key=preserve_client_ip.enabled,Value=true
```

Expected:

```text
Key: preserve_client_ip.enabled
Value: true
```

Retest the connection and verify that the 
application can identify the original client IP.

## Gateway Load Balancer

### How It Works

Gateway Load Balancer operates at Layer 3 and distributes network 
traffic across a fleet of virtual network appliances. GWLB uses the
GENEVE protocol over UDP port 6081 to encapsulate and forward traffic 
to virtual network appliances.

Unlike ALB and NLB, GWLB is designed for deploying and scaling 
third-party security appliances.

### Common Use Cases

- Deploying third-party virtual firewalls.
- Intrusion Detection Systems (IDS).
- Intrusion Prevention Systems (IPS).
- Centralized network traffic inspection.
- Scaling security appliances across Availability Zones.
- Integrating virtual network appliances into VPC traffic paths.

### Troubleshooting Scenarios

### Scenario 1: Traffic Bypasses the Security Appliance

**Problem**

A company deploys GWLB to inspect traffic, but some application traffic reaches its destination without passing through the virtual firewall.

**Investigation**

**Step 1: Check VPC route tables.**

```bash
aws ec2 describe-route-tables \
  --filters Name=vpc-id,Values="$VPC_ID" \
  --query 'RouteTables[*].{ID:RouteTableId,Routes:Routes[*].[DestinationCidrBlock,GatewayId,NetworkInterfaceId]}'
```

Possible output:

```text
RouteTableId: rtb-123456

Routes:
  Destination: 0.0.0.0/0
  GatewayId: igw-123456
```

The default route points directly to an Internet Gateway instead of the intended GWLB endpoint.

**Step 2: Check GWLB endpoint status.**

```bash
aws ec2 describe-vpc-endpoints \
  --filters Name=vpc-id,Values="$VPC_ID"
```

Expected:

```text
VpcEndpointType: GatewayLoadBalancer
State: available
```

**Step 3: Check security appliance traffic logs.**

Review the virtual firewall logs and compare them with the application traffic.

Possible output:

```text
No matching traffic found
```

This indicates that the traffic may not be reaching the inspection appliance.

**Possible Causes**

- Route table does not point to the GWLB endpoint.
- Some subnets use a different route.
- Incorrect GWLB endpoint association.
- Security appliance is unavailable.
- Traffic is routed through an alternative path.

**Resolution**

Correct the VPC route tables and ensure that the 
intended traffic passes through the GWLB endpoint.

Retest and verify that the traffic appears in the virtual firewall logs.
