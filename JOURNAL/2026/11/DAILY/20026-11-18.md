# Today's Focus: Caching Server

## CloudFront

### How It Works

Amazon CloudFront is an AWS CDN service that distributes 
content through a global network of edge locations.

CloudFront retrieves content from configured origins, such as 
Amazon S3 buckets, Application Load Balancers or custom HTTP servers.

### Common Use Cases

- Delivering static website content.
- Distributing images, CSS and JavaScript files.
- Accelerating API and web application delivery.
- Protecting applications with AWS WAF.
- Integrating with Amazon S3 and Application Load Balancer.
- Reducing traffic to origin servers.
- Supporting global content distribution.


### Troubleshooting Scenarios

### Scenario 1: Low Cache Hit Ratio Causes High Origin Traffic

**Problem**

A company uses CloudFront to deliver static website content.

However, the origin server continues receiving a large number 
of requests, resulting in increased server load.

**Investigation**

**Step 1: Check CloudFront response headers.**

```bash
curl -I https://static.example.com/images/logo.png
```

Possible output:

```text
HTTP/2 200
Content-Type: image/png
Cache-Control: no-store
X-Cache: Miss from cloudfront
```

The response indicates that CloudFront is not serving the 
object from its cache.

**Step 2: Repeat the request and check the cache status.**

```bash
curl -I https://static.example.com/images/logo.png
```

Possible output:

```text
HTTP/2 200
Content-Type: image/png
Cache-Control: no-store
X-Cache: Miss from cloudfront
```

Repeated cache misses indicate that CloudFront is not 
effectively reusing the cached object.

**Possible Causes**

- Origin responses contain `Cache-Control: no-store`.
- Cache TTL is configured too low.
- Cache policy disables caching.
- Different query strings or request headers generate different cache keys.
- The requested objects are not eligible for caching.

**Resolution**

- Configure appropriate `Cache-Control` response headers.
- Review the CloudFront cache policy and TTL settings.
- Avoid unnecessarily including query strings, cookies or headers in the cache key.
- Cache static resources for an appropriate duration.

Retest:

```bash
curl -I https://static.example.com/images/logo.png
```

Expected:

```text
HTTP/2 200
X-Cache: Hit from cloudfront
```

A cache hit indicates that CloudFront is serving 
the object from its edge cache.

### Scenario 2: CloudFront Returns HTTP 502 Bad Gateway

**Problem**

Users access a website through CloudFront but receive HTTP 502 errors.
The origin server is configured to use HTTPS.

**Investigation**

**Step 1: Check the CloudFront response.**

```bash
curl -I https://cdn.example.com
```

Possible output:

```text
HTTP/2 502
X-Cache: Error from cloudfront
```

This indicates that CloudFront encountered an error 
while communicating with the origin or processing the request.

**Step 2: Check the origin HTTPS certificate.**

```bash
openssl s_client \
  -connect origin.example.com:443 \
  -servername origin.example.com
```

Possible output:

```text
Verify return code: 62
Hostname mismatch
```

The certificate hostname does not match the origin domain
name used by CloudFront.

**Step 3: Check the origin configuration.**

```bash
aws cloudfront get-distribution-config \
  --id "$DIST_ID" \
  --query 'DistributionConfig.Origins.Items[].{DomainName:DomainName,ProtocolPolicy:CustomOriginConfig.OriginProtocolPolicy}'
```

Expected fields:

```text
DomainName: origin.example.com
OriginProtocolPolicy: https-only
```

Compare the configured origin domain with 
the certificate's Subject Alternative Names (SANs).

**Possible Causes**

- Origin SSL/TLS certificate is expired.
- Certificate hostname does not match the configured origin domain.
- Certificate chain is incomplete or invalid.
- CloudFront cannot resolve the origin domain.
- Origin does not support the required TLS protocol or cipher configuration.

**Resolution**

- Configure a valid SSL/TLS certificate.
- Ensure the certificate covers the origin domain name.
- Verify that the complete certificate chain is installed.
- Confirm that the origin supports the required TLS configuration.
- Verify origin DNS resolution and connectivity.

Retest:

```bash
curl -I https://cdn.example.com
```

Expected:

```text
HTTP/2 200
```

## AWS Global Accelerator

### How It Works

AWS Global Accelerator is a networking service that improves the
availability and performance of applications for global users.

Unlike CloudFront, Global Accelerator does not cache application content.

Instead, it provides static anycast IP addresses and routes 
incoming traffic through the AWS global network to healthy application endpoints.

### Common Use Cases

- Accelerating global application traffic.
- Supporting multi-Region applications.
- Improving application availability.
- Providing static anycast IP addresses.
- Routing traffic to healthy regional endpoints.
- Supporting TCP and UDP applications.
- Implementing multi-Region failover.
- Supporting blue/green deployments using traffic controls.

### Troubleshooting Scenarios

#### Scenario 1: Global Accelerator Does Not Route Traffic to an Expected Endpoint

**Problem**

A company deploys applications in two AWS Regions.

However, users continue receiving traffic from an unexpected regional endpoint.

**Investigation**

**Step 1: Check the accelerator configuration.**

```bash
aws globalaccelerator list-accelerators
```

Expected:

```text
AcceleratorArn: arn:aws:globalaccelerator::123456789012:accelerator/xxxx
Enabled: true
```

**Step 2: Check endpoint group configuration.**

```bash
aws globalaccelerator describe-endpoint-group \
  --endpoint-group-arn "$ENDPOINT_GROUP_ARN"
```

Possible output:

```text
EndpointGroupRegion: us-east-1
TrafficDialPercentage: 100

EndpointDescriptions:
  - EndpointId: alb-use1
    Weight: 128
    HealthState: HEALTHY
```

Review the endpoint group Region, traffic dial and endpoint weights.

**Step 3: Check endpoint health.**

```bash
aws globalaccelerator describe-endpoint-group \
  --endpoint-group-arn "$ENDPOINT_GROUP_ARN" \
  --query 'EndpointGroup.EndpointDescriptions[].{Endpoint:EndpointId,Health:HealthState,Weight:Weight}'
```

Expected:

```text
Endpoint: alb-use1
Health: HEALTHY
Weight: 128
```

Compare the health and weight settings across regional endpoint groups.

**Possible Causes**

- Incorrect endpoint group configuration.
- Unexpected traffic dial percentage.
- Endpoint weights are configured incorrectly.
- One regional endpoint is unhealthy.
- Traffic is being routed according to endpoint health and client location rather than the expected Region.

**Resolution**

- Verify endpoint group configuration.
- Adjust traffic dial percentages when controlling regional traffic.
- Review endpoint weights.
- Restore unhealthy endpoints.
- Verify that regional traffic distribution matches the intended architecture.

Retest and monitor the traffic distribution.


## Redis (Amazon ElastiCache for Redis OSS)

### How It Works

Redis is an in-memory data store commonly used as a caching layer for applications.

Instead of retrieving frequently accessed data from a database every time, 
applications can store frequently used data in Redis.

### Common Use Cases

- Application data caching.
- Database query result caching.
- User session storage.
- Frequently accessed configuration data.
- API response caching.
- Real-time counters and statistics.
- Distributed application state.

### Troubleshooting Scenarios

#### Scenario 2: Redis Memory Usage Is High and Keys Are Being Evicted

**Problem**

A Redis cluster experiences high memory usage.

Some frequently accessed keys unexpectedly disappear, 
causing increased database requests.

**Investigation**

**Step 1: Check Redis memory usage.**

```bash
redis-cli -h "$REDIS_ENDPOINT" -p 6379 INFO memory
```

Possible output:

```text
used_memory_human:3.8G
maxmemory_human:4.0G
```

Redis is approaching its configured memory limit.

**Step 2: Check eviction statistics.**

```bash
redis-cli -h "$REDIS_ENDPOINT" -p 6379 INFO stats
```

Possible output:

```text
evicted_keys:25000
keyspace_hits:15000
keyspace_misses:35000
```

A large number of keys have been evicted.

**Step 3: Check ElastiCache CloudWatch metrics.**

```bash
aws cloudwatch get-metric-statistics \
  --namespace AWS/ElastiCache \
  --metric-name Evictions \
  --dimensions Name=CacheClusterId,Value="$CACHE_CLUSTER_ID" \
  --start-time "$START_TIME" \
  --end-time "$END_TIME" \
  --period 300 \
  --statistics Sum
```

Expected:

```text
MetricName: Evictions

Sum: 25000
```

The CloudWatch metric confirms that Redis has evicted a 
significant number of keys during the selected period.

**Possible Causes**

- Cache memory capacity is insufficient.
- Application stores too much data in Redis.
- TTL values are too long.
- Large objects consume excessive memory.
- The eviction policy removes frequently accessed keys under memory pressure.

**Resolution**

- Review Redis memory usage and key distribution.
- Remove unnecessary cached data.
- Set appropriate TTL values.
- Review the configured eviction policy.
- Scale up the cache node or add shards when required.
- Monitor memory usage and eviction metrics.

Retest:

```bash
redis-cli -h "$REDIS_ENDPOINT" -p 6379 INFO memory
```

Expected:

```text
used_memory_human:2.5G
maxmemory_human:4.0G
```

Monitor the Evictions metric to verify that memory pressure has been reduced.
