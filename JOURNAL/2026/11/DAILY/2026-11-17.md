# Today's Focus: Firewall

## AWS Network Firewall

### How It Works

AWS Network Firewall is a managed network security service 
that inspects and controls traffic entering, leaving or 
passing through a VPC.

### Common Use Cases

- Controlling outbound internet access.
- Inspecting traffic between VPCs.
- Blocking unauthorized network traffic.
- Applying stateful traffic filtering.
- Monitoring network traffic through CloudWatch Logs and Amazon S3.

### Troubleshooting Scenarios

### Scenario 1: Firewall Blocks Legitimate Application Traffic

**Problem**

An EC2 application cannot access an external API after Network Firewall rules are introduced.

Example:

```text
curl: (28) Connection timed out
```

**Investigation**

**Step 1: Test external connectivity.**

```bash
curl -v --connect-timeout 5 https://api.example.com
```

Possible output:

```text
Connection timed out after 5000 milliseconds
```

**Step 2: Check Network Firewall status.**

```bash
aws network-firewall describe-firewall \
  --firewall-name "$FIREWALL_NAME"
```

Expected:

```text
FirewallStatus:
  Status: READY
```

Verify that the firewall and its endpoints are available.

**Step 3: Review Network Firewall Alert Logs.**

If logging is enabled:

```bash
aws logs tail /aws/network-firewall/alert \
  --since 30m
```

Possible output:

```text
{
  "event_type": "alert",
  "src_ip": "10.42.10.25",
  "dest_ip": "203.0.113.10",
  "dest_port": 443,
  "proto": "TCP",
  "alert": {
    "action": "blocked"
  }
}
```

This is an illustrative log example.

**Step 4: Review firewall policy association.**

```bash
aws network-firewall describe-firewall \
  --firewall-name "$FIREWALL_NAME" \
  --query 'Firewall.FirewallPolicyArn'
```

Expected:

```text
arn:aws:network-firewall:us-east-1:123456789012:firewall-policy/example-policy
```

Review the associated Stateless and Stateful Rule Groups in the AWS console or through the corresponding `describe-firewall-policy` command.

**Possible Causes**

- Stateful rule blocks the destination.
- Stateless rule drops the packet.
- Destination port is not permitted.
- Rule priority or default action is incorrect.
- Traffic is not being forwarded to the stateful engine as intended.

**Resolution**

Correct the firewall policy to permit the required traffic while maintaining the intended security restrictions.

Retest:

```bash
curl -v --connect-timeout 5 https://api.example.com
```

Expected:

```text
HTTP/2 200
```

The actual response depends on the external API.

### Scenario 2: Asymmetric Routing Causes Connection Failures

**Problem**

Applications experience intermittent connection failures when 
traffic passes through Network Firewall.

Some connections succeed while others time out.

**Investigation**

**Step 1: Review VPC route tables.**

```bash
aws ec2 describe-route-tables \
  --filters Name=vpc-id,Values="$VPC_ID" \
  --query 'RouteTables[*].{ID:RouteTableId,Routes:Routes[*].[DestinationCidrBlock,TransitGatewayId,NetworkInterfaceId]}'
```

Expected:

```text
RouteTableId: rtb-123456

Routes:
  Destination: 0.0.0.0/0
  NetworkInterfaceId: eni-firewall-endpoint
```

Verify that the intended forward and return paths use the correct firewall endpoints.

**Step 2: Check Transit Gateway attachments.**

```bash
aws ec2 describe-transit-gateway-attachments \
  --filters Name=resource-type,Values=vpc
```

Expected:

```text
ResourceType: vpc
State: available
```

Confirm that the inspection VPC attachment is available.

**Step 3: Check Network Firewall Flow Logs.**

```bash
aws logs tail /aws/network-firewall/flow \
  --since 30m
```

Review source IP, destination IP, traffic direction and flow status.

**Possible Causes**

- Forward and return traffic use different firewall endpoints.
- Transit Gateway routing is incorrect.
- Appliance mode is not enabled where required.
- Traffic bypasses the intended inspection path.
- Stateless rules forward only one traffic direction to the stateful engine.

**Resolution**

Correct VPC and Transit Gateway routing to ensure 
symmetric traffic flows through the same firewall endpoint.

For centralized inspection architectures using Transit Gateway, enable 
appliance mode on the inspection VPC attachment where required.
Also ensure that stateless rules handle both request and response 
directions consistently.

Retest application connectivity and verify both directions in the firewall logs.

## AWS Web Application Firewall (WAF)

## How It Works

AWS WAF protects web applications by inspecting incoming HTTP/HTTPS requests and 
evaluating them against configured Web ACL rules.

## Common Use Cases

- SQL Injection protection.
- Cross-Site Scripting (XSS) protection.
- IP address filtering.
- Rate limiting.
- Blocking suspicious HTTP requests.
- Protecting web applications against common web exploits.

## Troubleshooting Scenarios

### Scenario 1: Legitimate Requests Are Blocked by AWS WAF

**Problem**

A legitimate user cannot submit a payment request.

Example:

```text
HTTP/1.1 403 Forbidden
```

The application is healthy, but AWS WAF blocks the request.

**Investigation**

**Step 1: Check Web ACL configuration.**

```bash
aws wafv2 get-web-acl \
  --name "$WEB_ACL_NAME" \
  --scope REGIONAL \
  --id "$WEB_ACL_ID"
```

Expected:

```text
WebACL:
  Name: bank-web-acl
  DefaultAction:
    Allow: {}
```

Review the configured rules and their actions.

**Step 2: Check sampled requests.**

```bash
aws wafv2 get-sampled-requests \
  --web-acl-arn "$WEB_ACL_ARN" \
  --rule-metric-name "$RULE_METRIC_NAME" \
  --scope REGIONAL \
  --time-window StartTime="$START_TIME",EndTime="$END_TIME" \
  --max-items 100
```

Possible output:

```text
SampledRequests:
  - Request:
      URI: /payment/submit
      HTTPMethod: POST
    Weight: 1

    RuleWithinRuleGroup:
      RuleId: SQLi_BODY
```

The request matches a SQL injection detection rule.

**Step 3: Review WAF logs.**

```bash
aws logs tail /aws/waf/bank-web-acl \
  --since 30m
```

Check the terminating rule, action and matching request details.

**Possible Causes**

- SQL injection detection produces a false positive.
- Request body contains characters matching an XSS rule.
- Custom rule is too restrictive.
- Managed rule group blocks a legitimate request.

**Resolution**

Review the matching rule and determine whether the request is genuinely malicious.

If it is a false positive, apply a narrowly scoped rule exclusion or exception rather than disabling the entire managed rule group.

Retest the original payment request.

Expected:

```text
HTTP/2 200
```

The legitimate request should be allowed.

### Scenario 2: Excessive Requests Trigger Rate Limiting

**Problem**

Users receive HTTP 403 when accessing an application after a large number of requests.

Example:

```text
HTTP/1.1 403 Forbidden
```

**Investigation**

**Step 1: Check WAF Web ACL metrics.**

```bash
aws cloudwatch get-metric-statistics \
  --namespace AWS/WAFV2 \
  --metric-name BlockedRequests \
  --dimensions Name=WebACL,Value="$WEB_ACL_NAME" Name=Region,Value="$AWS_REGION" Name=Rule,Value="$RULE_METRIC_NAME" \
  --start-time "$START_TIME" \
  --end-time "$END_TIME" \
  --period 300 \
  --statistics Sum
```

Possible output:

```text
Datapoints:
  - Sum: 8500
    Unit: Count
```

A large number of requests have been blocked by the specified rule.

**Step 2: Review WAF logs.**

```bash
aws logs tail /aws/waf/bank-web-acl \
  --since 30m
```

Review:

- Client IP address.
- Request URI.
- Request frequency.
- Rate-based rule action.

**Step 3: Check ALB request metrics.**

```bash
aws cloudwatch get-metric-statistics \
  --namespace AWS/ApplicationELB \
  --metric-name RequestCount \
  --dimensions Name=LoadBalancer,Value="$ALB_METRIC_NAME" \
  --start-time "$START_TIME" \
  --end-time "$END_TIME" \
  --period 300 \
  --statistics Sum
```

Possible output:

```text
Datapoints:
  - Sum: 120000
    Unit: Count
```

Compare the request volume with the normal baseline.

**Possible Causes**

- A malicious client generates excessive requests.
- A legitimate client exceeds the configured rate limit.
- An application retry mechanism generates repeated requests.
- Rate-based rule scope is too broad.

**Resolution**

Adjust the rate-based rule scope or threshold based on the intended traffic pattern.

If the traffic is malicious, retain the blocking policy.

Retest and verify that legitimate users can access the application while excessive requests remain restricted.


## AWS Shield

## How It Works

AWS Shield is a managed DDoS protection service that protects 
AWS resources against Distributed Denial of Service attacks.

## Common Use Cases

- Protecting public-facing applications.
- Mitigating network-layer DDoS attacks.
- Protecting application availability.
- Providing advanced DDoS event visibility.
- Supporting application-layer DDoS mitigation with AWS WAF.
- Protecting supported CloudFront, Route 53, ALB and other AWS resources.

## Troubleshooting Scenarios

### Scenario 1: Sudden Traffic Spike and Application Unavailability

**Problem**

A public-facing bank application experiences a sudden increase in 
incoming traffic.

Legitimate users experience slow responses or cannot access the application.

Example symptoms:

```text
HTTP 503 Service Unavailable
HTTP 504 Gateway Timeout
```

**Investigation**

**Step 1: Review ALB request metrics.**

```bash
aws cloudwatch get-metric-statistics \
  --namespace AWS/ApplicationELB \
  --metric-name RequestCount \
  --dimensions Name=LoadBalancer,Value="$ALB_METRIC_NAME" \
  --start-time "$START_TIME" \
  --end-time "$END_TIME" \
  --period 300 \
  --statistics Sum
```

Possible output:

```text
Datapoints:
  - Sum: 500000
    Unit: Count
```

Compare the traffic volume with the normal baseline.

**Step 2: Check ALB response metrics.**

```bash
aws cloudwatch get-metric-statistics \
  --namespace AWS/ApplicationELB \
  --metric-name HTTPCode_ELB_5XX_Count \
  --dimensions Name=LoadBalancer,Value="$ALB_METRIC_NAME" \
  --start-time "$START_TIME" \
  --end-time "$END_TIME" \
  --period 300 \
  --statistics Sum
```

Possible output:

```text
Datapoints:
  - Sum: 15000
    Unit: Count
```

A high number of ALB-generated 5XX responses indicates that the 
load balancer is experiencing service-side errors.

**Step 3: Check AWS Shield Advanced attack information.**

For Shield Advanced subscriptions:

```bash
aws shield list-attacks
```

Possible output:

```text
AttackSummaries:
  - AttackId: example-attack-id
    ResourceArn: arn:aws:elasticloadbalancing:us-east-1:123456789012:loadbalancer/app/example
```

Investigate the affected resource and attack details.

Note: `list-attacks` provides Shield Advanced attack visibility. 
Shield Standard does not provide the same attack-event API visibility.

**Step 4: Review AWS WAF logs.**

```bash
aws logs tail /aws/waf/bank-web-acl \
  --since 30m
```

Identify unusual request patterns, suspicious client IPs and rate-based 
rule actions.

**Possible Causes**

- Network-layer DDoS attack.
- Application-layer HTTP flood.
- Large volumes of automated requests.
- Legitimate traffic surge combined with insufficient backend capacity.

**Resolution**

Use AWS Shield protection and review whether Shield Advanced is appropriate for the application.

For application-layer attacks, configure AWS WAF protections such as managed rules and rate-based rules.

Review ALB and backend capacity to ensure the application can handle legitimate traffic.

Monitor CloudWatch metrics and verify that normal users can access the application again.
