# 2026-09-03

## Today's Focus: Production incidents

## Category: Memory pressure

### Summary

An application encountered a `java.lang.OutOfMemoryError: GC overhead limit exceeded` while processing unusually large batch files.

### Troubleshooting Steps

1. Check the application logs, and found that the error occurred during a file processing.
2. Check the file size, and found that the file was 10 times larger than the average file size.
3. Check the JVM configuration, `-Xms` was set to 1024m, -`-Xmx` was set to 2048m
4. Check the VM memory, and found that the VM had 8GB of memory allocated

### Impact

The batch processing failed 

### Root Cause

The large batch workload caused high memory consumption, and the configured JVM heap was
insufficient to handle the workload efficiently.

### Resolution

1. Increase the memory of the VM to 16GB 
2. Increase the JVM heap size by setting `-Xms` to 4096m and `-Xmx` to 8192m
3. Rerun the batch processing and the batch processing completed successfully

### Lessons Learned

#### Why does batch size causes memory pressure?

Because the larger the batch, the more data the application may need to hold in memory at the same time,
if the memory required by the batch exceeds the available heap capacity, the JVM will perform GC more 
frequently, leading to `GC overhead limit exceeded` error.

#### How to configure `-Xms` and `-Xmx`?

- `-Xms` -- initial heap size
- `-Xmx` -- maximum heap size

Don't set `-Xmx` equal to the entire container/VM server memory limit

#### What is GC overhead limit?

The GC overhead limit is a JVM mechanism designed to detect when the JVM is spending too much time
performing Garbage Collection while recovering too little memory.

#### Why increasing memory is just a mitigation?

Increasing the memory of the VM and the JVM heap size was an effective mitigation because it 
provided additional memory headroom for the large batch workload

#### How to address the root cause?

Optimize the application's memory usage and batch processing logic, for example by using streaming or chunk-based
processing

#### About GC Log and Heap Dump

- GC Logs: show how the JVM behaves over time
  - Enabled GC logging through JVM startup parameters: `-Xlog:gc*:file=/path/gc.log:time,uptime,level,tags:filecount=5,filesize=20M`
  - GC logging normally has a low runtime overhead, but it generates disk I/O and consumes disk space.
    Log rotation should be configured using options such as `filecount` and `filesize`
- Heap Dump: a snapshot of the JVM heap at a specific point in time
  - Enabled automatic Heap Dump through JVM startup parameters: `-XX:+HeapDumpOnOutOfMemoryError
    -XX:HeapDumpPath=/path/to/dump`
  - These parameters have almost no impact during normal operation. However, generating a Heap Dump during an OOM
    can cause significant disk I/O and temporarily consume CPU/resources. The dump can also be several GB in size.
- jstat (command): monitors JVM heap utilization and GC activity in real time
  - `jstat -gcutil <PID> 1000`
- jcmd (command): creates a Heap Dump of the real-time running JVM for further memory analysis
  - `jcmd <PID> GC.heap_dump /tmp/heap.hprof`
